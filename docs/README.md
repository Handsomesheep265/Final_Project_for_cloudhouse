    +  token持久化的实现：每次打开自动续期，登录一次就不用再登
    +  退出登录立即吊销旧token：保证用户退出登录后，旧token已被拉入黑名单，下次需要重新登录

  当时run起来的时候还以为是后端连接失败了，但是试了其他功能的接口都没有问题很正常，就只有筛选这里出问题，也是有点慌了呀，但是好在实际上没有出大问题，反而也让我了解到了项目出现问题的时候排查问题是有一套逻辑和流程的。
  以下是我总结的一套排查问题的sop(?)总的来说就是由表及里，从前端一路往后端摸
      + 确认问题。eg. 点击“贴纸”按钮，页面没有任何反应
      + 确认开发环境是否造成影响，以及不同浏览器的表现是否一致
      + 按键盘上的F12，切换至控制台观察是否有红色的报错信息
    这些都是现象层面的，比较表象，通常还要到通信层面判断请求是不是真的发出去了
      + 按F12切换到Network，点击按钮
        + 若无请求，多半是前端ts逻辑层出问题了
        + 若有请求，先看status
          + 如果状态码为4开头，有可能是接口路径的问题
          + 如果是5开头，就是后端服务器的问题了
        + 看请求参数：检查前端传给后端的参数是不是筛选对应的category：’贴纸‘
    前端部分排查
      + 事件是否真的挂载了
      + 看看点击按钮时，代码中的实际传参，如果不小心传了id=0或者undefined给后端，导致后端返回空数组，前端就以为没变化直接静默了
      + 是否是路由跳转失败
      + 可能有父级元素拦截了点击事件，得去查看前端代码的结构
      + 异步加载未完成：按钮绑定的方法可能依赖了后端返回的数据，后端返回的数据还没有加载出来，用户就点击了按键，方法里因为没拿到数据就直接return，使得用户看着像点击了却没有反应（点击事件和数据“加载”有时间差）
    后端部分排查
      + 确认接口连通性：使用Postman测试接口，看是否返回数据
  配合大肥鱼协助调查，发现是乌龙事件啊，前后端的代码都没有出现什么问题。但是这样也反映出页面设计上的一些漏洞
